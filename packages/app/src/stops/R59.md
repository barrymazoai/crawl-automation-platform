# R59 handoff — CRAWLV3-132

Changes are left in the shared working tree. Nothing was committed, pushed, deployed, or started.

## Behavior

- Known completed/failed activity outcomes keep the original reserve/work/release command sequence.
  Business activities arm their own journal. Unknown outcomes, or a release transaction rejected for
  pending cleanup, enter `resource-execution-stop-proof-v1` and poll durable stop proof. The bounded
  window defaults to 150 seconds with 5-second polls (`resources.stopVerificationSeconds` and
  `resources.stopVerificationPollSeconds`). Unknown shutdown ends with `RESOURCE.CLEANUP_UNVERIFIED`;
  it does not release capacity or retry the business operation.
- Workers associate the activity's exact permit/workflow/run with provider identities. OCR records
  a pre-submission identifier, browser rounds record a sentinel before spawning plus streamed page
  targets and host identity, and Codex records its owned PID, host, start time and execution ID.
- A valid synchronous OCR response proves completion. An optional job-control adapter performs
  query/cancel/query under a configurable 120-second deadline, covering the 90-second hard limit
  plus margin. Cancel acceptance is
  not stop proof. Browser recovery closes the exact target once and checks absence read-only at most
  three times, under its own deadline. User control stops recovery. Codex proof follows observed
  child-process closure. Cleanup success never converts a business failure into success.
- The permit row lock serializes identity, proof and release writes. Both the release adapter and
  the migration's database trigger reject missing or incomplete stop proof, including legacy rows.
  A closed workflow, no pending activities and elapsed time alone are insufficient.
- The existing resources permits API returns cleanup state, attempts, original failure, identities
  and stop receipts. Missing legacy proof appears as `CLEANUP_UNVERIFIED`.
- Requested/granted/released events have database timestamps and matching workflow logs. The
  10/30/60-second resource-wait polling policy is unchanged.

## Required rollout and remaining limitations

Apply `database/v3/042_permit_stop_proof.sql` through the existing migration API before loading the
new workers/API. No new credentials or automatic startup configuration are needed. Existing held
permits without executor receipts remain held; do not substitute workflow age for missing proof.

The OCR service changes add durable caller job IDs and status/cancel endpoints. The exported
`OcrHttpJobControl` is wired through the worker's `ocrClient` with the same endpoint and transport;
`processing.ocrApi.jobControl` defaults off. Enable only after all routed backends have been upgraded
and verified. Legacy correlation IDs remain explicitly unsupported; unknown outcomes stay held.
See `docs/operations/machines.md` for the client settings and required timing relationship.

Provider stop actions run in the original worker's cleanup path. The resource stop activity checks
durable receipts; it does not guess how to kill execution on another host. Worker loss, user control,
missing browser-round results, and unavailable provider controls remain actionable unverified
recovery items. A browser round lacking its final result keeps its sentinel unproved even if all
known targets were closed, because an unreported page cannot be ruled out.
