# 成分表处理改造方案：先照抄，再解析

日期：2026-11-04　状态：方案待批准（未写代码）　来源：KAN-253 Nature's Way 测试中发现

## 1. 为什么要改

现在每换一个网站，成分表就会因为格式问题大批进 Review，修一条规则又冒出下一条：

- 这次 Nature's Way：已处理的 84 个产品里 35 个进 Review，全部是成分表提取类原因。其中 `TEXT.LABEL_PARENT_INVALID`（子成分挂错上级）19 个，近 30 天全部 DTC 一共才 23 个。
- `TEXT.CITATION_INVALID`（出处对不上）：模型抄出处时多一个空格、少一个 ®、换个撇号就失败。2026-09-29 统计过，85% 的这类 Review 其实引用是对的。
- 规则是一条条补的：2026-10-12 放宽上级规则时，411 个已存答案里有 176 个只因为"复方里的小标题"被拒。

根本原因：现在让模型**一步同时做两件事**，一是理解成分表结构，二是逐字给出每个字段在原文里的出处。再用一张"一条不过整张作废"的规则表去核对。模型在理解时会顺手改写格式，结构也是它猜的，所以格式差异和结构猜错都会卡住产品。

## 2. 现在的流程（代码位置）

| 环节 | 现状 | 位置 |
|---|---|---|
| 找成分表（网页） | 把 HTML 转成带格子标记的文字行（`pageText(..., { rowCells: true })`），截出 Facts 区域 | `packages/channels/dtc/src/label-core.ts`（GNC、Swanson 各有自己的 label-core） |
| 找成分表（图片） | Windows OCR（PP-OCRv5）返回每段文字及其坐标框 `lines[{text, score, polygon}]` | `apps/ocr-service/ocr_server.py` |
| 拆成结构 | Codex 文本模型输出 `label-extraction/1`：每行的类型（`nutrient` / `group_header` / `blend_total` / `blend_component`）、用量状态、`parentRowIndex`，每个字段都带出处（`fromLine`/`toLine`/`text`） | `packages/processing/src/text`，契约 `packages/v3-contracts/src/label-extraction.ts` |
| 核对出处 | 出处文字必须和原文行一字不差 | `packages/processing/src/text/protocol/anchored-decoder.ts`、`resolve-anchor.ts` |
| 规则检查 | 十几条规则，任何一条不过整个产品进 Review | `packages/v3-contracts/src/label-rules/` |
| 下游 | 配方、补全、推送 Supply Smart 都读 `label-extraction/1` 的结果 | `packages/processing/src/assembly`、`packages/app/src/product-delivery` |

## 3. 新流程：两步

### 第一步：照抄（还原原表，不做任何理解）

输出新契约 `label-transcript/1`：成分表、Other Ingredients、份量这几段，每段一行一行原样还原。

- 每行记录：各格原文（`cells[]`）、缩进层级、是否粗体或标题、来自原文哪几行。
- **网页上本来就是表格的：不用模型。** 直接按 DOM 读取：`<table><tr><td>`、用 div 拼的格子（现有的 rowCells / markerCells 逻辑），缩进来自前导空格、`&nbsp;`、嵌套列表或缩进样式。
- **图片：先用代码按 OCR 坐标排版。** 坐标相近的文字合成一行，按表头（Amount Per Serving、% Daily Value）的横坐标分列，按左边距和表格左边缘的距离算缩进层级。
  - 可选的现成库：PaddleOCR 自带的表格结构识别（PP-StructureV3 的 SLANet / SLANeXt），和 Windows 上现有的 OCR 同一套技术，能从图片直接输出表格 HTML。官方文档说明 SLANeXt 的单元格坐标不可用，只能用它的 HTML 结构。阶段 2 和"按坐标自己排"做对比，再决定用哪个。
- **模型只在代码排不出来时兜底：** 比如成分表是一段话，或者 OCR 读乱了顺序。这时模型的任务只有"把每行原文照抄成格子"，不判断类型、不建上下级。照抄结果按行和原文比相似度：先统一空格、大小写、® ™、各种撇号和破折号，再比较。**数字和单位必须完全一致**，不一致就退回。

### 第二步：解析（用代码，结果固定）

把照抄出来的行解析成现有的 `label-extraction/1` 结构，**下游完全不用改**：

- 每行拆出成分名、数字加单位、%DV、注释符号（†、*）。
- 上下级按原表的缩进和"复方总量行"来定：复方行之后、缩进更深的行属于它，缩进回到原级就结束。括号里列出的复方成分也拆成子成分。
- 份量行（Serving Size、Servings Per Container），以及 Other Ingredients（按逗号拆，括号内不拆）。
- 出处由照抄阶段的行号自动生成，不会再出现"出处对不上"。
- 代码拆不出的个别行（比如用量写在名字里的特殊写法）交给模型解释这一行，结果仍按第 4 节的内容规则核对。

## 4. 校验：内容严、格式松、结构降级

| 类别 | 处理 |
|---|---|
| 成分名、数字加单位必须在原文里出现（统一格式后比较） | **保留，不过就进 Review**（防止模型编数据） |
| 单位必须在白名单内；同义写法列成明确对照表（µg = mcg 等） | 保留 |
| 出处逐字一致、行序、上下级规则 | **改成警告**，不再进 Review |
| 复方归属不确定 | 交付时标 `blendStructure: uncertain`，子成分只给名字，不给推算的用量 |
| 成分完全拿不到 | 仍进 Review（符合"最低可用"：有成分、功效、剂型即可） |

## 5. 复用什么、新写什么

- **复用：**
  - 各渠道 label-core 的 HTML 预处理、截取 Facts 区域的逻辑；
  - OCR 服务已有的 `lines + polygon` 输出；
  - `label-extraction/1` 契约和整个下游；
  - 规则表里的内容类规则；
  - R2 里保存的原始页面和 OCR 结果（重放不需要重新抓取）；
  - Server 一的标签规则回放工具（`~/kan226-sim`，只读、按 R2 覆盖）。
- **新写，以及为什么写：**
  - `label-transcript/1` 契约。现有契约把"抄"和"解释"绑在一起，需要拆开。
  - HTML → 照抄稿。现有的只输出带标记的纯文字，没有保留格子和缩进。
  - OCR 坐标 → 照抄稿。坐标现在没被用来排版。
  - 行解析和上下级构建。现在这部分是模型猜的。
  - 统一格式后的整行相似度比较。找现成库，比如维护中的编辑距离库，实施时确认，不自己写算法。
  - 兜底的"照抄格子"模型任务的提示词和解码。

## 6. 分阶段上线

0. **基线：** 统计各渠道近 30 天成分表 Review 的原因分布，作为对比基准。
1. **网页表格（DTC、GNC、Swanson 的文字成分表）：** 实现照抄和解析，用 R2 里已存的页面文字新旧各跑一遍。
   - 比较：通过率；新旧都通过的产品，成分集合是否一致；新增放行的随机抽 50 个人工核对。
   - 达标后才上线，上线由配置开关按渠道开启，旧流程保留可回退。
2. **图片 OCR：** 按坐标排版，并和 PP-Structure 表格识别对比，同样先回放再上线。
3. **处理积压：** 用保存的原件重跑现有的成分表 Review，不重新抓页面。新结果推送前先给你看数量。

## 7. 风险和应对

| 风险 | 应对 |
|---|---|
| 模型编的成分或用量混进来 | 第 4 节第一条：名字、数字和单位必须在原文里出现 |
| 统一格式时把不同的东西当成一样（mg 和 mcg、1,000 和 1.000、%DV 当成用量） | 只统一纯格式字符；数字、单位、百分号严格比较；单位同义写法用明确对照表 |
| 复方归属错，下游误读用量 | 标 `uncertain`，不给推算用量；下游不拿它算剂量 |
| 读成别的产品或别的规格的成分表 | 现有的规格归属检查不变 |
| 新规则放进了错的数据 | 原件都在 R2，可以重新处理、重新推送；上线前做 50 个人工抽查 |

## 8. 需要你决定的

1. 结构不确定、但成分齐全的产品，是否带着 `uncertain` 标记直接交付？（建议：交付）
2. 兜底模型用哪个、什么推理强度、并发多少？（现在成分表用的是 Luna medium）
3. 先做哪个渠道？（建议先做 DTC，它的问题最多；GNC、Swanson 也是网页表格，可以一起回放）
4. 上线门槛：比如新旧都通过的产品成分一致率 ≥ 98%，抽查 50 个错误 ≤ 1 个。
