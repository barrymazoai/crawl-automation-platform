# 成分表处理改造方案：先照抄，再解析

日期：2026-11-04（同日按 Demo 结果修订）　状态：方案待批准，生产代码未改　来源：KAN-253 Nature's Way 测试

## 1. 为什么要改

现在每换一个网站，成分表就会因为格式问题大批进 Review。修好一条规则，马上又冒出下一条：

- Nature's Way（2026-11-04）：162 个产品里 54 个卡在成分表 Review。近 30 天全部 DTC 的 `TEXT.LABEL_PARENT_INVALID`（子成分挂错上级）一共 23 个，其中 19 个出自这一次。
- `TEXT.CITATION_INVALID`（出处对不上）：模型抄出处时多一个空格、少一个 ®、换个撇号就失败。2026-09-29 统计过，这类 Review 里 85% 的引用其实是对的。
- 规则是一条条补的：2026-10-12 放宽上级规则时，411 个已存答案里有 176 个只是因为"复方里的小标题"被拒。

根本原因：现在让模型**一步同时做两件事**：理解成分表结构，以及逐字给出每个字段在原文里的出处。之后再用一张"一条不过、整张作废"的规则表去核对。模型在理解时会顺手改写格式，结构也是它猜的，所以格式差异和结构猜错都会卡住产品。另外，网页成分表在交给模型之前就被拍平了：每一格单独一行，缩进和"哪几格属于同一行"的信息都丢了，模型只能自己猜结构。

## 2. 现在的流程（代码位置）

| 环节 | 现状 | 位置 |
|---|---|---|
| 找成分表（网页） | HTML 被转成"一格一行"的文字（`pageText(..., { rowCells: true })`），然后截出 Facts 区域 | `packages/channels/dtc/src/label-core.ts`（GNC、Swanson 各自有 label-core） |
| 找成分表（图片） | Windows OCR（PP-OCRv5）返回每段文字和坐标框 `lines[{text, score, polygon}]`，**只用来挑图**；挑中的图交给视觉模型 | `apps/ocr-service/ocr_server.py`、`packages/processing/src/vision` |
| 拆成结构 | 文本或视觉模型输出 `label-extraction/1`：每行的类型、用量状态、`parentRowIndex`，每个字段都带出处 | `packages/processing/src/text`、`vision`；契约在 `packages/v3-contracts/src/label-extraction.ts` |
| 核对出处 | 出处必须和原文逐字一致 | `packages/processing/src/text/protocol/anchored-decoder.ts`、`resolve-anchor.ts` |
| 规则检查 | 十几条规则，任何一条不过，整个产品进 Review | `packages/v3-contracts/src/label-rules/` |
| 下游 | 配方、补全、推送 Supply Smart 都读 `label-extraction/1` | `packages/processing/src/assembly`、`packages/app/src/product-delivery` |

## 3. Demo 结果（2026-11-04）

Demo 只读：用的是 R2 里存好的页面、OCR 结果和图片，没写数据库，也没推送任何东西。代码在会话临时目录，数据副本在 Server 一 的 `~/kan253/demo`，都不进 git。

### 网页（有表格结构）：代码直接读 HTML，不用模型

| 样本 | 产品 | 新方式拆出 | 旧方式 Review 中救回 | 两边都成功时用量一致 |
|---|---|---|---|---|
| Nature's Way（div 拼的表格） | 145 | **145** | **50/50** | 91/94，剩下 3 个是新方式更准 |
| GNC（标准 HTML 表格） | 21 | **21** | — | **21/21** |
| 其他 DTC 网站（13 个站） | 45 | 30 | 12/17 | 两组合计 **39/39** |
| Swanson（纯文本 `<pre>`） | 13 | 0 | — | Demo 没做按行拆 |

- 两边都成功时，成分名不一致的主要原因是**旧方式自己前后拆法不统一**：同一个"果蔬复方"，有的产品拆成子成分，有的整行当一个名字。新方式每次都按同一规则拆。
- 没拆出来的分三类：
  - 页面上根本没有成分表结构，只有营销文案（需要模型兜底）；
  - Swanson 的纯文本（要补按行拆）；
  - 用通用 CSS 类拼出来的表格（jarrow、natrol，要补"重复行"识别）。

### 图片：只用 OCR 不行，照抄要交给视觉模型

| 做法（100 个产品：50 个完成、50 个 Review） | 拆出 | 旧方式 Review 中救回 | 两边都成功时用量一致 |
|---|---|---|---|
| 只用 OCR 坐标排版 | 51 | 24 | 80% |
| **视觉模型照抄 + 代码解析**（Luna medium，平均 46 秒一张） | **96** | **46/50** | 85% |

- 只用 OCR 的问题：
  - OCR 认错字，自己没法纠正（"nTurmeric"、"sophorap a"）；
  - 长名字换行后接不回来；
  - 多列用量（1 片 / 3 片 / 4 片）会挤进同一格。
- 视觉模型只做照抄：每行的各格原文、缩进、是否粗体。抄得很准，换行、多列、商标符号都能处理。
- 数字有分歧的 5 处，逐一对照原图：
  - **新方式对 3 处**：212 mcg（旧方式读成 212 mg，差一千倍）、钾 200 mg、芦丁 50 mg；
  - 旧方式对 1 处（核黄素 25 mg）；
  - 两边都错 1 处（字很小的维生素 E）。
- 其余用量不一致的，大多是 Demo 的解析规则没覆盖到的写法：
  - 顺势疗法的 "1X"；
  - 两栏排版把用量写进名字；
  - 旧方式把 "95% proanthocyanidins" 里的 95 当成了用量。
- 用 OCR 核对数字时，1,289 个用量里有 351 个在 OCR 文字里找不到。原因混在一起：OCR 认错字、挑到了别的图、写法不同。**不能直接当硬门槛。**

## 4. 新流程：两步

### 第一步：照抄（还原原表，不做任何理解）

输出新契约 `label-transcript/1`：成分表、Other Ingredients、份量这几段，一行一行原样还原。

- 每行记录：各格原文（`cells[]`，多列用量各占一格）、缩进层级、是否粗体或标题、出处位置。
- **网页表格：用代码直接按 DOM 读，不用模型。** 包括：
  - `<table><tr><td>/<th>` 表格，注意行首的 `<th scope="row">` 是成分名，不是表头；
  - 用 div 拼的行和列；
  - 用通用 CSS 类拼的"重复行"；
  - `<pre>` 或纯文本，按行和列的对齐拆。
  
  一格里写成 "复方名: A, B, C" 的，原样保留，交给第二步处理。
- **图片：交给视觉模型照抄。** 它只抄每行的格子、缩进和粗体，不判断类型、不建上下级、不改拼写。
- **页面上没有成分表结构的（营销文案、要点列表）：** 也交给模型照抄"像成分表的那部分"。抄不出来就是没有成分表。

### 第二步：解析（用代码，结果固定）

把照抄稿解析成现有的 `label-extraction/1`，**下游完全不用改**：

- 每行拆出成分名、主用量（数字 + 单位，含 DFE/RAE；括号里的 "(63%)"、"(1000 IU)" 单独保存）、%DV、注释符号。
- 上下级按这些规则确定：
  - 缩进、"复方总量行"；
  - 复方行之后、缩进更深或没有用量的行属于它；
  - 没有用量的小标题彼此平级，后一个出现时结束前一个；
  - 一个有用量的顶层成分出现时，结束前面没有用量的子成分。
- 固定写法：
  - 一格里写成 "复方名: A, B, C"，以及复方下缩进一级的逗号列表 → 复方加子成分；
  - "Includes 4 g Added Sugars" → 用量写在名字里；
  - 顺势疗法浓度（1X、6C、HPUS）；
  - 两栏排版的营养成分（用量写进名字的，从名字里拆出来）。
- 出处由照抄稿的行号自动生成，不会再出现"出处对不上"。
- 代码拆不出的个别行，交给模型解释这一行，结果按第 5 节核对。

## 5. 校验：内容严、格式松、结构降级

| 类别 | 处理 |
|---|---|
| 网页：成分名、主用量必须在原文里出现（统一空格、大小写、®™、撇号和破折号后比较） | **保留，不过就进 Review** |
| 图片：主用量交叉核对。和 OCR 一致就通过；不一致时，让视觉模型**独立再读一遍这一行**，两次一致才算数 | 两次仍不一致：用量标"不确定"，不推算；产品照常交付成分 |
| 单位必须在白名单内；同义写法用明确的对照表（µg = mcg 等） | 保留 |
| 出处逐字一致、行序、上下级规则 | **改成警告**，不再进 Review |
| 复方归属不确定 | 交付时标 `blendStructure: uncertain`，子成分只给名字，不给推算的用量 |
| 成分完全拿不到 | 仍进 Review（"最低可用"：有成分、功效、剂型即可） |

## 6. 复用什么、新写什么

- **复用：**
  - 各渠道 label-core 截取 Facts 区域的逻辑；
  - OCR 服务的 `lines + polygon`，以后用于交叉核对；
  - 现有视觉模型调用（app-server 客户端），换成"照抄"任务；
  - `label-extraction/1` 契约和整个下游；
  - 规则表里的内容类规则；
  - R2 里保存的原件（重放不需要重新抓取）；
  - Server 一 的标签规则回放工具（`~/kan226-sim`）。
- **新写，以及原因：**
  - `label-transcript/1` 契约。现有契约把"抄"和"解释"绑在一起，要拆开。
  - HTML → 照抄稿。现有流程会把表格拍平。
  - 视觉"照抄"任务的提示词和输出格式。Demo 里已经验证过一版。
  - 行解析和上下级构建。现在是模型猜的。
  - 主用量的标准化和交叉核对。找现成的维护中的库来做文本比较，不自己写算法。

## 7. 分阶段上线

0. **基线：** 统计各渠道近 30 天成分表 Review 的原因分布。
1. **网页表格（DTC、GNC、Swanson 的文字成分表）：** 补齐 Demo 没覆盖的写法（纯文本、通用 CSS 类表格、表格里的价格和脚注行），用 R2 已存页面做大样本回放。
   - 指标：通过率；两边都成功时用量一致率；新放行的随机抽 50 个人工核对。
   - 达标后由配置开关按渠道开启，旧流程保留，可以回退。
2. **图片：** 视觉模型照抄 + 代码解析 + 数字二次核对，同样先回放再上线。
   - 回放会调用模型，事先确认模型、推理强度、并发和总量。
3. **处理积压：** 用保存的原件重跑现有的成分表 Review，不重新抓页面。推送前先给你看数量。

## 8. 风险和应对

| 风险 | 应对 |
|---|---|
| 模型编的成分或用量混进来 | 网页：名字、用量必须在原文里；图片：用量和 OCR 或第二次独立读数一致才算数 |
| 小字、模糊的标签读错数字（Demo 里两种方式都出现过） | 二次核对；不一致就标"不确定"，不用模型猜的数 |
| 统一格式时把不同的东西当成一样（mg 和 mcg、1,000 和 1.000、%DV 当成用量） | 只统一纯格式字符；数字、单位、百分号严格比较；同义写法用明确的对照表 |
| 复方归属错，下游误读用量 | 标 `uncertain`，不给推算的用量 |
| 读成别的产品或别的规格的成分表 | 现有的规格归属检查不变 |
| 新规则放进了错的数据 | 原件都在 R2，可以重新处理、重新推送；上线前人工抽查 50 个 |
| 图片照抄的模型成本 | 和现在视觉线一样是每张图一次调用（Demo 平均 46 秒）；二次核对只针对有分歧的行 |

## 9. 需要你决定的

1. 结构不确定、但成分齐全的产品，是否带着 `uncertain` 标记直接交付？（建议：交付）
2. 图片照抄和二次核对用哪个模型、什么推理强度、并发多少？（Demo 用的是 Luna medium、并发 3，和现在视觉线一致）
3. 先做哪部分？（建议先做网页表格，Demo 已经证明可行，而且不花模型成本；图片紧随其后）
4. 上线门槛：比如两边都成功时用量一致率 ≥ 98%（剩下的分歧要对照原图确认新方式对），抽查 50 个错误 ≤ 1 个。
