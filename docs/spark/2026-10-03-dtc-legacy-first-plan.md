# DTC 修正计划：只采集材料，后续统一处理

2026-10-03；父票151，采集183，转换184，混合155/178，详情完整性148。

## 执行优先级修正（用户澄清，2026-10-04）

目标是让原有 DTC 流程持续产出可用结果，并覆盖不同网站和商品。遇到差异先判断它实际影响什么；不能把网站资料不完美一律当作程序 bug，也不能为补齐无关紧要的证明长期卡住一个样本。

- 不影响产品身份和主要结果的差异，采用已有材料、允许的共用策略或可选字段留空，记下局限后继续。缺失内容不编造。
- 明确会串产品、错用不同配方、丢失关键材料的问题才阻断受影响项；该项留证据、清理并记录后，其他已授权的商品和网站继续测试。
- 相同原因集中修在可复用流程中，不为每个商品追加专用补丁。直接测试检验实际结果，不再为每种正常网站差异增加新的证明步骤。
- 按实际完成的产品、规格与网站覆盖汇报进展，区分需要立即修复的共性阻塞和可以后续处理的小问题。

已确认的代表性规则：同一产品的多个网站规格只提供一张可用 Facts 时，允许共用该图，不再要求图上必须有包装数量或网站明确声明共用。规格 ID、选项、SKU、价格仍取各规格原始材料；这是用户接受的处理规则，不伪称网站证明了配方一致。确有多个不同 Facts 时仍做归属。该规则只是上述执行原则的一例。

落地顺序：将这项共性阻塞作最小修改，用 Tongkat 已保存材料直接验证交接和下游，然后回到其余代表性商品/站点测试；不重抓该网页、不覆盖旧 Review。规则记录不等于代码已实现或整条链路已验收。

1. 复用站点脚本和旧runHarvest。模型学习真实导航、展开、规格切换和全图库采集方法，保存脚本给后续适用商品复用。

3. 删除6170cfa新增的强制post-capture Codex复核和原文字段/子串选择。materials.json只列原件路径和规格对应关系，固定程序校验文件留存并映射到已有下游数据结构，不重新解析材料。
4. 规格切换后材料独立则直接使用对应HTML/图片；仍混合则走已有DtcMixedGallery OCR/原图归属。URL变化本身不证明材料独立。证据不足只隔离对应规格，不猜默认值、不丢掉其他可处理规格。
5. 保留现有多产品组合判定、Facts和enrich处理，输入改用原始商品区域HTML与图片。产品内容在后续处理，不在采集和转换重复提取。其他channel共享流程不改。

采集完成先精确关任务页、停止任务进程并归档，之后的处理使用留存材料。公司必须登录才能采集则跳过。未知用户页不关闭。失败或取消的业务任务不自动重试，旧原件与Review保留。

## 多品牌拆分与排队补充方案（2026-10-03，待实施）

用户要求多品牌拆成独立任务排队慢慢运行。本轮只核对代码和旧票、记录方案，尚未修改业务代码或启动新批次。

历史依据：CRAWLV3-93 的 2026-09-30 用户决定明确“一个网站三个品牌就是三个独立任务，最小单位为一个站点上的一个品牌”。旧39169c2的crawlTarget/crawlPortfolio已有直属品牌分路，但在一次调用中逐品牌执行；V3的dtcBrandSources与持久化brand_scan已支持每品牌一条来源和扫描任务。CRAWLV3-147进一步要求入口自动发现同站/跨域品牌。当前applySiteAnalysis只创建/匹配品牌来源，并不提交扫描；BrandScanRunner默认并发4，claim无DTC专属并发限制。因此不能把已有来源拆分称为“入口到独立任务串行排队”已经验收。

建议复用现有任务、brand_scan和商品队列：

1. 站点分析确认真实品牌与对应入口；同站品牌分别绑定目录，直属子品牌使用其官方站点。一家品牌的官网跳商城仍是同一品牌；vendor别名不直接拆成新品牌。已明确要求采集的多品牌站点不能被旧skill默认排除卖场的规则误挡。
2. 在现有应用结果后衔接品牌任务入队，一次提交中的每个已核实品牌各有独立任务ID和状态。创建来源与入队必须有持久化、可恢复的交接；重复提交同一请求不能重复排队。父记录汇总子任务，不占用浏览器等待子任务完成。
3. 每个品牌任务只发现自己的商品目录，再把产品交给现有商品队列。单品仍按原始材料采集→混合规格条件处理→固定转换→原Facts/enrich流程执行，不新增内容解析。品牌目录完成与该品牌商品处理完成分别统计。
4. DTC品牌任务先限定同时运行1个，DTC商品浏览器采集同样保持1个，由现有资源许可协调；其他channel并发不改。每项完成浏览器阶段立即归档、关闭精确任务页并释放已停止的执行资源，后续OCR不占着浏览器。
5. 单品牌失败保留Review及证据；确认停止和清理后继续下一个，不自动重试。必须登录才能继续采集的公司跳过。现有scan按started_at超时重领的逻辑需要检查DTC重复启动风险，不能仅靠时间过期就重开仍在运行的浏览器任务。

实站验收补齐：同站多个真实品牌→独立任务/独立结果；中间品牌失败或跳过后后项仍执行；重复提交不重复执行；暂停/恢复与清理。复用既有候选站：Nature's Truth先验证品牌与vendor别名；Solaray验证混合variant；Vimerson/PhytAge覆盖其他站点结构。同站第二商品验证方法复用；Klean Athlete按用户要求跳过。多品牌原始例子Nutriessential在93有明确用户授权，可在截图候选不能提供真实多品牌正例时使用。只在Mini直接验证，不新增或运行单元测试。147跟踪入口拆分排队，151跟踪整体验收，155/183/184继续各自职责。

实施落点补充（方案，尚未编码）：

代码职责边界（用户进一步澄清）：站点分析、任务编排、品牌目录发现、单品材料采集分别作为业务模块。现有原生入口已有agent/analysis.ts、agent/catalog.ts、agent/product-capture.ts，apps/worker/src/browser/dtc-agent-parts.ts把它们接到同一DtcCaptureAgent执行器；共享Ego/Codex运行、方法库、归档与清理不等于一次调用混跑全部阶段。分析只输出核实品牌/入口/证据，允许有限代表页核实身份；编排程序读取结果创建持久化任务；目录任务直接从指定品牌入口开始并只输出该品牌商品链接；单品任务只收原始材料。分析所得入口、路线和方法应留存并传给适用的后续任务。不会先启动整站收割、遇到多品牌再退出并从头重跑，也不会让单品采集自己调用建任务接口。品牌任务仍核对所属品牌，但不重新做全站品牌发现。

- 入队：在现有站点分析应用路径增加明确的“应用并入队”操作语义，保留仅保存来源的既有调用。复用PostgresSiteAnalyses的事务和oncePerRequest回执，让来源、独立brand_scan队列记录、分析到扫描的关联一起提交；返回各品牌scanId及未入队原因。失败回滚，不使用内存循环依次发请求作为唯一交接。
- 调度：在现有BrandScanRunner/PostgresBrandScans.claim增加DTC通道的持久化暂停状态与并发1限制；领取时在数据库内约束，多个API执行器也不能各领一个。其他channel维持现状。按排队次序取任务，暂停只停止领取新任务，取消仍走已有取消/清理。商品队列继续使用原控制，不把品牌扫描暂停误称为所有已入队商品也停止。
