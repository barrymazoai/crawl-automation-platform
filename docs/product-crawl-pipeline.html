Target Architecture · Review Draft

产品爬取自动化
端到端流程真源

这张图描述当前迁移后的目标架构与实现状态。核心边界：Skill 只用于 DTC 浏览器爬取；Mac Processing 对全部图片调用无状态 OCR HTTP API；Codex 只处理固定索引里的页面与 OCR 文字，不视觉读取图片；入库由仓库内 Product DB Adapter 直连同一产品库并回读。

DTC：capture → process → ingest → cleanup Amazon：Link Monitor pipeline → verify → cleanup Capture：DTC Browser / Mac Adapter Browser：Windows A · 2 进程 OCR API：Windows B · 无状态 HTTP Process：Mac mini · 2 进程 · Luna Medium 数据库：Product DB Adapter 直连
01 · Non-negotiable boundaries

四条不能混淆的边界

后面所有流程都必须服从这四条。任何实现如果越过边界，就算功能暂时能跑，也不属于目标架构。

Skill 只在 Capture

只有 DTC 的 Windows Browser Capture 加载 crawl-products。Amazon 是 Mac Process 内的固定 Adapter；OCR、Process、Review、Ingest 都不读取 Skill。

OCR 是无状态 HTTP API

Mac 对全部画廊图片逐张调用接口，只接收文字、坐标和置信度。没有 OCR Job、OCR Artifact，也不判断 Benefits、Form 或 Health Function。

Codex 是受控转换器

代码按 ASIN/变体边界构造固定输入；DTC 可逐产品调用，Amazon 沿用最多 50 条一批但按 ASIN 严格对齐。Codex 不浏览网站、不遍历目录、不控制队列。

数据库写入有门禁

每个变体独立入库；必须先完成证据校验，再由 Product DB Adapter 写入，最后按 channel + externalId 回读成功才允许清理。

02 · Deployment topology

三个执行面＋一个无状态 OCR API

Railway 只调度 Browser、Processing、Ingest/Cleanup Job。OCR 服务虽然部署在另一台 Windows，但它不领取队列任务，只同步响应 Mac 发出的图片 HTTP 请求。

CLOUD · RAILWAY

控制面

只管状态和调度，不处理商品内容。

  • URL Router：DTC / sales_channel
  • 创建 Job DAG
  • 租约、超时、重试
  • DTC Artifact 与 Amazon 运行状态
  • needs_review 与节点状态
→
WINDOWS A · BROWSER

Browser Node

两个 Codex/Chrome Worker；只有这里使用 Skill。

  • 网站发现与页面访问
  • 目录、变体、SKU、价格
  • HTML / JSON / 全部图片
  • EvidenceBundleV1
→
MAC MINI · PROCESSING + DATA

处理与入库节点

同时承载两条本地工作流：处理 Windows 交来的 DTC EvidenceBundle；原样运行 Amazon Link Monitor 管线。最终统一校验并直连同一产品库。

  • Amazon Link Monitor 原生模块
  • 逐图调用 OCR HTTP API
  • 本地 OCR checkpoint 与证据切片
  • Luna Medium 结构转换
  • ProductBatchV2 Schema 校验
  • 事务入库和数据库回读
HTTP DEPENDENCY · WINDOWS BOCR API：POST image → OCR JSON。无 Job、无租约、无 Artifact；服务端不保存流程状态。

A · DTC Browser Capture

普通品牌站由 Windows A 的 Browser Worker 领取 browser capability，使用 crawl-products Skill 和 Chrome，输出 EvidenceBundleV1。

B · Amazon 原生流水线

Mac mini 直接复用 Link Monitor 的 Amazon 搜索、变体解析、HTML 快照、规则清洗、Codex 清洗与 OCR 标签流程；不用 Skill，也不生成 EvidenceBundle。

C · 在最终数据契约汇合

DTC 和 Amazon 的原始证据存储方式不同，不强行统一。两条路径只在 ProductBatchV2、证据校验和 Product DB Adapter 处汇合。

DTC 跨机器使用 EvidenceBundle；Amazon 沿用 Link Monitor 本地文件断点并生成 ProductBatchV2，不新增中间 Bundle
03 · Reuse Link Monitor

Amazon 直接搬用现有 Link Monitor 流程

Amazon 不是通用网站，不需要重新设计一套 Adapter 产物。把原项目已验证的搜索、变体、快照、清洗、OCR 与入库模块搬进 Mac Worker；Railway 只包住任务状态、并发和 Review，不改变它们之间的本地数据流。

A1 · ROUTE + RUN

Railway 只负责调度

识别 Amazon 后把任务交给 Mac 上的 Link Monitor Runner。

  • sourceType=sales_channel
  • adapter=amazon
  • 记录 run、进度与控制指令
  • 不投递 DTC Browser Skill
A2 · DISCOVERY

真实 Chrome 扫 Amazon 搜索页

直接复用 amazon-search、browser、discovery。

  • 按 Amazon 品牌翻搜索页
  • 真实 Chrome CDP，非纯 fetch
  • 已知 ASIN 去重与增量发现
  • 页上限/风控/失败状态保留
A3 · VARIANTS + SNAPSHOT

解析变体家族并保存 HTML

直接复用 resolve-variants 与 snapshot。

  • 一个详情页解析整个 variation family
  • 每个 ASIN 保留独立身份
  • 完整 HTML 原子写成 ASIN.html.br
  • 中断后已完成结果不丢
A4 · CODE CLEAN

规则清洗本地 HTML

直接复用 extract-product；零模型、零网络。

  • 标题、品牌、价格、评分、库存
  • 图片 URL、Ingredients 原文
  • Bullets、Description、A+ 文本
  • 约 1.8MB HTML 压到语义所需片段
A5 · TEXT CODEX

两路 Codex 做文本语义清洗

直接复用 semantic-clean 与 clean 编排。

  • 每批最多 50 个产品
  • Mac 全局最多 2 个 Codex 进程
  • Nutrition 范围、功效、剂型、成分
  • 按 ASIN 对齐，逐批写 semantic checkpoint
A6 · PRODUCT BATCH

构造本地 ProductBatchV2

沿用 EnrichPayload 字段并补齐 SKU、family 与 Facts 契约。

  • externalId=ASIN
  • 每个变体单独一条 product
  • Nutrition evidence 与成分非空
  • product-batch.json 原子落盘
A7 · OCR STREAM

本地图片进入 OCR 流水线

直接复用 run-labels-ocr 与 ocr-label-pipeline。

  • 图片保存在 images/ASIN/00.jpg…
  • 单产品图片 OCR 并发 4
  • 每图原子写 00.ocr.json
  • 只用结构词筛出 Facts 候选
A8 · FACTS + FINAL SINK

Luna 解析 OCR 文本并写产品库

产品 OCR 完成即进 Codex 队列，不等待全量图片。

  • Luna 全局并发 2，不接收图片
  • 逐产品写 label.raw.json 断点
  • Adapter 写产品、挂牌、快照和 Formula
  • 按 channel + externalId 回读通过后才完成
Amazon 的真实中间状态，不是 Bundle

ASIN.html.br 是可离线重放的页面真源；images/ASIN/* 是图片真源；每图 *.ocr.json 是 OCR 断点；每产品 label.raw.json 是模型判定断点；product-batch.json 和 ingest-result.json 是结构化与回读断点。Railway 只读取进度和控制状态，不搬运这些同机文件。

迁移已落地

简化版 processAmazon 已删除。当前代码已迁入 Chrome CDP、搜索分页、变体家族、Brotli 快照、确定性提取、Nutrition 语义清洗、逐图 OCR 缓存、Facts 文本解析和 Product DB 回读门禁。

迁移后的模块边界

已迁入

amazon-search、browser、snapshot、extract-product、semantic-clean、ocr-label-pipeline、label-parse 与 Link Check 纯函数。

薄编排层

Railway 管 Job；Mac 保持 HTML、图片、OCR、label 与 batch 断点，同一 Job 重试直接复用。

新最终写入端

仓库内 Adapter 直接写入与 Link Monitor 相同的产品表，再按 channel + externalId 回读验证。

Windows A · DTC Browser Node

04
Mac mini · Processing Worker → Windows B OCR API

下载 DTC 证据并逐图调用 OCR HTTP API

Mac 不知道哪张图片有用，因此把全部画廊图片送入接口；接口同步返回 OCR JSON。

不用 Skill不用 CodexMac 调用代码 + 无状态 HTTP

DTC 输入

  • 从云端下载一次 EvidenceBundle
  • 读取 Manifest 全部 imageFiles
  • 校验 Bundle 与文件哈希
  • 建立图片 OCR checkpoint

逐图并发 HTTP 调用

  • 固定并发池 POST 多张图片
  • 当前实现 4 路，可配置上限
  • 接收文字 / 坐标 / 置信度
  • 失败按单图重试
  • 结果保存为本地 .ocr.json

明确不存在

  • 没有 OCR Job 或租约
  • 没有 OCRBundle 上传
  • 接口不保留业务状态
  • 接口不做任何语义判断
失败恢复与缓存边界

DTC 本地 checkpoint 以图片路径绑定 OCR 响应。Mac 重启后可复用已完成结果，只重试缺失或失败图片；本地证据丢失时从云端 EvidenceBundle 重新下载。Amazon 的恢复规则见上一节：直接复用 ASIN HTML、图片、.ocr.json、label.raw.json、product-batch.json 与 ingest-result.json。

Mac mini · deterministic preprocessor

按变体建立受限证据输入

程序使用本地 OCR 响应做机械整理，不让 Codex 自己遍历整个任务目录。

不用 Skill此步不用 Codex固定代码

机械处理

  • Schema 与哈希校验
  • 按 EvidenceItem 分组
  • 正文去导航/页脚/重复
  • OCR 空白和重复文本去除
  • 保留 source/image ID

可做的锚点

  • Facts 明确标题匹配
  • Ingredients 明确标题匹配
  • Directions 明确标题匹配
  • 低置信度 / OCR 失败

不能预判

  • 不能把营销句标成 Benefits
  • 不能生成 healthFunctions
  • 不能依据成分猜功能
  • 不能凭包装外观猜剂型
单产品 SemanticInput 包含什么
  • 结构化身份：variantId、SKU、价格、币种、商品 URL。
  • 索引明确列出的页面证据文件；不存在统一的“Product Details”字段，除非网页原文真的有该标题。
  • 全部非空 OCR 文本：有逻辑 image ID、置信度和坐标，供 Codex 做语义判断。
  • 索引不提供原图路径，Codex 不打开或视觉读取任何原图。

  • 归一 productForm
  • 解析 mainIngredients 层级
  • 营养单品范围判断
  • 每个结论引用 evidence ID

图片读取边界

  • 全部图片先由 OCR API 读取

  • OCR 行列含混时进入 Review

  • 不查找文件
  • 不管理 Job
  • 不自由写产物目录

三个语义字段的真实来源
  • mainIngredients：Facts/Ingredients OCR 和页面 Ingredients 原文；必须保留标签文字。
  • productForm：标题、变体、Directions、Serving Size 或 OCR 原文里明确出现的 capsule/softgel/liquid/gummy 等证据。
  • healthFunctions：Codex 从页面正文与全部 OCR 文本中识别明确支持/用途句，再映射为数据库词表。OCR API 本身不认识 Benefits。

不用 Skill机械全量校验可选受限语义复审

身份校验

  • externalId = 真实 variantId
  • SKU 与 EvidenceItem 一致
  • 每个可售变体独立
  • URL、价格、币种可追溯

语义校验

  • 成分对象字段齐全
  • category 属于固定枚举
  • 未知/未归组显式报告

  • FAIL/冲突 → needs_review artifact

  • OCR 没有 Facts，DOM 也没有 Ingredients/Formula。

  • SKU、variantId、价格在不同来源不一致。
  • 成分 taxonomy 无法稳定映射。

05 · Image truth pipeline

图片到底在哪里被“看懂”

关键区别：Browser 收集像素；Mac 把像素发给 OCR API；OCR 只读取字符；Codex 解释文字含义。这些不是同一个动作。

A · CAPTURE

全部画廊图片

Browser 下载所有图片，但不知道哪张是 Facts、Benefits 或 Directions。

B · HTTP OCR ALL

Mac 逐图调用接口

每张图片作为 HTTP 请求发出；OCR API 返回文字、坐标和置信度，不保存 Job 或 Artifact。

C · LOCAL INDEX

本地缓存与机械整理

Mac 保存 .ocr.json，去空、去重、保留 image ID；仅对明确 Facts 标题做字符串锚点。

D · CODEX TEXT

语义判断

Codex读取所有有效 OCR 文本与页面正文，识别功效、剂型和成分证据。

E · VALIDATE

结构校验或 Review

模型只解析 OCR 文字；OCR 结构冲突或无法形成合法成分行时停在 needs_review，不用视觉猜测补全。

OCR 不认识 Benefits

如果图片明确写着 “Benefits”，程序可以记录标题命中；如果只有“Supports brain and eye development”这类营销句，只有 Codex 语义阶段才能判断它是否支持某个 healthFunction。OCR API 只报告这句话存在。

没有统一 Product Details

系统只保存网页原始 HTML、可见正文和真实 DOM 标题。只有站点本身存在 “Product Details” 标题时才保留这个名称；否则一律称为页面原始正文片段，不能伪造成标准字段。

07 · State, concurrency, retention

状态、并发与文件生命周期

并发由代码和租约控制，不由 Prompt 决定。Railway 是队列真源；SQLite 只保存节点本地 checkpoint 和 outbox。

queued→ leased→ running→ completed→ 下游 Job 或retry_wait 或needs_review 或failed

成功分支

Capture、Process、Ingest、Read-back 全部通过；DTC 清理云端 Bundle 与 Mac 缓存，Amazon 清理本轮本地工作文件并保留必要运行摘要。

Review 分支

任何身份、证据或 taxonomy 冲突都会停止 Ingest；DTC 保留云端与本地证据，Amazon 保留 HTML、图片、OCR、label、batch 和 ingest 断点。

失败与重试

临时网络/节点错误进入 retry_wait；登录墙、验证码、范围歧义等不可自动解决问题进入 needs_review。

节点并发真源

Capture executors

Browser Windows 同时最多 2 个 DTC 网站；Mac 独立运行迁入的 Link Monitor Amazon Runner。两条来源流程不占用彼此的抓取进程池。

OCR HTTP API · Windows B

不领取 Railway Job；只接受 Mac 的图片请求并同步返回 JSON。接口无状态，服务并发由 HTTP Server 自身限制。

Mac mini Process

同时最多 2 个 Process Job；每个 Job 内用图片并发池调用 OCR API（当前 4 路），完成后再按单产品固定请求调用 Luna Medium。
